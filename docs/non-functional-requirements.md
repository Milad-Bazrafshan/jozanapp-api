# نیازمندی‌های غیروظیفه‌ای

## امنیت و حریم داده

- جداسازی Tenant باید در Query، Constraint و تست پوشش داده شود.
- رمز عبور فقط با الگوریتم مقاوم و تنظیمات قابل ارتقا hash می‌شود.
- Refresh Token قابل ابطال و دارای چرخه تعویض است.
- عملیات مالی، نمره، حضور، دسترسی و impersonation در Audit ثبت می‌شوند.
- داده حساس در log نوشته نمی‌شود.
- فایل فقط پس از کنترل Tenant، مالکیت و Permission دانلود می‌شود.
- Rate Limit برای login، بازیابی رمز و Endpointهای عمومی لازم است.

## کارایی اولیه

اهداف زیر برای بار معمول MVP و در صدک ۹۵ تعریف می‌شوند:

| عملیات | هدف |
|---|---:|
| خواندن‌های معمول API | کمتر از 500 ms |
| ثبت حضور یک کلاس 40 نفره | کمتر از 2 s |
| ذخیره پاسخ آزمون | کمتر از 500 ms |
| صفحات فهرست مدیریتی | حداکثر 50 رکورد در هر صفحه |

گزارش‌های سنگین و تولید PDF می‌توانند asynchronous باشند و وضعیت پردازش داشته باشند.

## دسترس‌پذیری و بازیابی

- هدف اولیه سرویس Pilot برابر 99.5% در ماه است.
- Backup دیتابیس روزانه و بازیابی آزمایشی دوره‌ای لازم است.
- هدف اولیه از دست‌رفتن داده حداکثر 24 ساعت و زمان بازیابی حداکثر 4 ساعت است؛ پیش از Production مالی باید سخت‌گیرانه‌تر شود.
- پرداخت و ارسال پاسخ آزمون باید در برابر retry امن باشند.

## زمان، تقویم و زبان

- زبان اولیه فارسی و جهت رابط RTL است.
- تمام Instantها در Backend با UTC پردازش می‌شوند.
- منطقه زمانی مؤسسه پیش‌فرض `Asia/Tehran` است و Rule برنامه آن را صریح ذخیره می‌کند.
- تاریخ شمسی قالب نمایش است؛ منبع محاسبات Instant و Local Date استاندارد است.
- اعداد فارسی و عربی هنگام جست‌وجو و ورود داده نرمال می‌شوند.
- متن و نام باید Unicode کامل را پشتیبانی کنند.

## سازگاری و دسترس‌پذیری رابط

- پنل‌ها Responsive و قابل استفاده در موبایل هستند.
- آخرین نسخه‌های پایدار مرورگرهای رایج هدف هستند.
- فرم‌ها با صفحه‌کلید قابل استفاده و خطاها به فیلد مرتبط متصل‌اند.
- رنگ تنها نشانه وضعیت نیست.

## مشاهده‌پذیری

- هر درخواست `traceId` دارد.
- log ساختاریافته شامل زمان، سطح، سرویس، traceId و tenantId غیرحساس است.
- Metricهای latency، error rate، pool دیتابیس، job و outbox جمع‌آوری می‌شوند.
- Health Check آمادگی و زنده‌بودن جدا دارد.
- هشدار برای خطای مکرر پرداخت، backlog رویداد و شکست job لازم است.

## کیفیت و تست

- قواعد Aggregate با Unit Test پوشش داده می‌شوند.
- Repositoryها و Tenant Isolation با Integration Test واقعی PostgreSQL بررسی می‌شوند.
- مسیرهای اصلی MVP تست End-to-End دارند.
- Migration فقط forward و نسخه‌شده است.
- تست مجوز باید Permission، Scope و رابطه دامنه‌ای را جداگانه پوشش دهد.
- قرارداد API در CI تولید و تغییر ناسازگار آن بررسی می‌شود.

## نگهداری داده

- سیاست مدت نگهداری Audit، Attempt Event، فایل و داده مالی پیش از Production تعیین می‌شود.
- حذف حساب کاربر به معنی حذف خودکار سوابق مالی و آموزشی نیست.
- داده‌های مشمول حذف یا ناشناس‌سازی باید براساس نوع رکورد سیاست مستقل داشته باشند.

## موارد باز

- `Open`: اهداف نهایی RPO/RTO محیط Production.
- `Open`: محل استقرار و الزامات نگهداری داده داخل کشور.
- `Open`: سیاست رضایت و نگهداری اطلاعات افراد زیر سن قانونی.
- `Open`: حجم مورد انتظار کاربران هم‌زمان در آزمون آنلاین.
